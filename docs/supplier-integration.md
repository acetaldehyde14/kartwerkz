# Supplier integration

## Principle

Supplier-specific logic never lives in the order controller/service. Every
interaction goes through a `SupplierAdapter` strategy interface, selected by
`Supplier.integrationMethod`:

```ts
interface SupplierAdapter {
  submitProductionPackage(pkg: ProductionPackage): Promise<SupplierSubmissionResult>;
}
```

```
SupplierIntegrationMethod: MANUAL | EMAIL | API | WEBHOOK | PORTAL
```

## Implemented today: `ManualFulfillmentAdapter`

The only adapter with real behavior. An admin reviews the approved order in
`/admin`, clicks "Send to Supplier", and the system:

1. Verifies the order's current artwork revision has an `APPROVED`
   `ArtworkApproval` (`isRevisionApprovedForProduction` — see
   `docs/database.md`). Refuses otherwise; there is no code path that can
   send unapproved artwork to production.
2. Builds a `ProductionPackage`: order reference, kart manufacturer/model,
   graphics design, full customization (colours, driver name/number/flag,
   logo placements), material finish, the approved artwork's object key, and
   any manufacturing notes the admin adds.
3. Creates a `SupplierOrder` row (`status: PENDING` → admin manually marks
   `SUBMITTED` once they've actually emailed/handed off the package to the
   real-world supplier).
4. Transitions the `Order` to `SENT_TO_SUPPLIER` via `OrderStatusService`.

This is intentionally manual because an automated integration doesn't exist
with the real supplier yet, and the spec is explicit: don't fake one.

## Stubbed for later: `EMAIL` / `API` / `WEBHOOK` / `PORTAL`

Each has a class implementing `SupplierAdapter` that currently throws
`NotImplementedException` with a clear message, so adding a real integration
later means implementing one method on one class — no changes to
`OrdersModule`, `SuppliersController`, or the admin UI beyond possibly
surfacing new per-supplier config fields.

- **EMAIL**: would render the `ProductionPackage` into a templated email
  (reuse the `send-email` BullMQ queue) with the approved artwork attached
  or linked via a signed URL.
- **API**: would call the supplier's REST/GraphQL API with mapped fields;
  needs per-supplier field-mapping config, not yet modeled.
- **WEBHOOK**: would POST the package to a supplier-provided URL with a
  shared-secret signature, mirroring how `/webhooks/stripe` is verified.
- **PORTAL**: would be a read-only view exposing pending `SupplierOrder`s to
  a logged-in supplier user — would need a new `SupplierUser` auth path,
  intentionally out of scope until a specific supplier requests it.

## What a production package does _not_ contain

Print-ready output (exact dimensions, bleed, cutlines, supplier-specific
templates) is **not** generated by this application. The browser-rendered
livery preview is an approximation for the customer and for the admin's
sanity check, not a substitute for the supplier's own artwork templates.
Admins are expected to prepare true production-ready files manually (using
the approved proof as the source of truth for _what_ to produce) and attach
them to the `SupplierOrder` as `productionPackageObjectKey` before marking it
submitted. Automating that conversion is future work, not assumed to exist.
